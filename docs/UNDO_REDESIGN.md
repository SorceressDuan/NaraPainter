# 结构性撤销改造方案

给决策者看的：**结论在最前面，技术细节在后面。** 这份文档只做设计，还没有写代码。

## 一、一句话结论

**改成「整份图层顺序的快照」，代价很小，值得做，而且可以分三步走、中途不推翻任何东西。**

## 二、现在的问题（用大白话说）

### 撤销栈是怎么工作的

每次改动都往撤销栈里压一条「怎么改回去」的说明。改像素的说明很直接：
「这层原来长这样，现在长这样」。但改**图层结构**（新增、删除、复制）的说明，
现在写成的是：「把第 3 行那层删掉」——**用"第几行"来记位置**。

### 为什么编组之后就不行了

「第几行」这个说法有三个致命毛病：

1. **它不知道"父子关系"。** 把一个图层放进文件夹，这个动作在"第几行"里根本表达不出来——
   行号没变，但父子关系变了。
2. **它覆盖不了"一整棵子树"。** 删掉一个文件夹，它下面的图层也一起消失了，
   但撤销说明里只记了"删掉这一层"。撤销之后，那些子图层要么回不来，要么回得来但**失去了爸爸**
   （`ParentId` 指向一个已经不存在的文件夹）。
3. **它会在半路静默失败。** 恢复动作里有一句「如果这行不在列表里就直接返回」——
   万一状态对不上，它会**悄悄地什么都不做**，界面和文档就此错位，而且不报错。

### 还有一处必须一起处理

现在的删除是「删一行 + 删一个图层」（`DocumentViewModel.cs:299-307`，不递归）。
所以删掉一个文件夹时，它的子图层会留下来、但 `ParentId` 指向一个**已经不存在的文件夹**。

**这个 bug 在模型层改造完成的那一刻就已经生效了**，值得单独说清楚它的表现：

| 时间点 | 删掉一个文件夹后，里面的图层 |
| --- | --- |
| 模型层改造**之前** | 还看得见——那时渲染是平铺遍历整个列表，不认父子关系 |
| 模型层改造**之后**（现在） | **从画面上消失**——渲染改成从"没有父节点的图层"开始走树，悬空的子图层永远走不到 |

也就是说：**子图层现在还在文档里、还在图层面板上、数据没丢，但画不出来，也没有任何提示。**
用户看到的是"删了文件夹，里面的图也一起没了"——这其实是对的行为，
但它**不可撤销**，而且正确性纯属巧合（是渲染遍历方式的副作用），不是设计出来的。
这次改造要把它变成明确的、可撤销的语义。

这个必须和撤销改造一起解决。

## 三、问题一：改成什么样的表达方式？

### 两个候选

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| **A. 快照整个图层顺序** | 每次结构性操作前后各存一份「图层列表 + 每层的父子关系」 | ✅ **选这个** |
| B. 只记录变化的子树 | 只存「哪几个图层被移动/删除了」 | ❌ 不选 |

**为什么不选 B：** 编组/解组/拖拽的组合太多了（放进文件夹、拖出文件夹、拖到文件夹顶部、
解组后子层回到文件夹原来的位置……），每一种都要单独写一份"变化前后"的记录，
写漏一种就是一个静默 bug。而 A 对**所有**结构性操作都用同一套逻辑，没有漏的可能。

### 方案 A 具体存什么

存的**不是像素**，是「谁、在哪、归谁管」：

```
一份快照 = 图层列表（按绘制顺序）
         + 每层的：所在的文件夹、是不是文件夹、可见性、不透明度、混合模式、名字
```

**关键决定：快照存的是"指向图层的指针"，不是图层内容的拷贝。**

这一点非常重要，因为它同时解决了性能和正确性：

- **性能**：拷一份 4000×3000 画布的一层像素是 **48 MB**。
  20 个图层就是 **960 MB**——撤销一次能把内存打爆。
  存指针的话，1000 个图层的一份快照只有 **约 8 KB**。
- **正确性**：图层对象保持是**同一个**。这一点至关重要，因为**改名字、改不透明度**
  这些撤销说明也指向同一个图层对象。如果快照恢复时造了新的图层对象，
  那些"改名字"的撤销就会作用在一个已经不在文档里的旧对象上——
  **按 Ctrl+Z 看起来像没反应**。这是这个方案里最容易踩的坑。

### 好消息：这套机制已经在用了

「整份顺序的快照」**不是新发明**，`ReorderLayers`（拖拽排序）现在就是这么做的：

```
存的：改动前的完整顺序、改动后的完整顺序
撤销：把顺序恢复成"改动前"
重做：把顺序恢复成"改动后"
```

所以这件事的本质是：**把已经验证过的做法，从"只有排序用"推广到"所有结构性操作用"。**

## 四、问题二：对现有 318 个测试有什么影响？

### 直接回答：影响很小，几乎不用改测试

我查了全部测试，结论如下：

| 检查项 | 结果 |
| --- | --- |
| 调用「新增图层」的测试 | **1 处**（`TransformTests.cs:187`，画布尺寸调整用） |
| 调用「复制图层 / 删除图层 / 拖拽排序」的测试 | **0 处** |
| **断言结构性撤销行为的测试** | **0 处** |
| 断言图层顺序/可见性/混合合成的测试 | 20 余条，全部在 `DocumentModelTests.cs`，**直接测文档模型、不经过撤销栈** |

**所以：没有任何一条现有测试会因为这次改造而失效。** 需要重写的测试是 **0 条**。

`TransformTests.cs:187` 那一处只是「加一层，然后测画布尺寸调整」，
它不关心撤销栈里存的是什么，改造后照常通过。

### 但这恰恰说明另一件事：结构性撤销**现在是完全没有测试覆盖的**

这不是好消息的背面，这是**风险提示**：

> 现在「新增图层 → Ctrl+Z → 图层消失」这条最基本的路径，**没有任何自动化测试**。
> 如果改造时改坏了，**测试不会报警**。

所以这次改造必须**先把测试补上，再改实现**——先写测试让它对旧实现通过（描述现状），
再改实现让同一批测试对新实现通过。这样改造才有安全网。

### 需要新补的测试（改造的一部分）

| 测试 | 覆盖什么 |
| --- | --- |
| 新增图层后撤销/重做 | 目前零覆盖 |
| 删除图层后撤销/重做 | 目前零覆盖 |
| 复制图层后撤销/重做 | 目前零覆盖 |
| **删除一个文件夹，撤销后子图层回来且父子关系正确** | 新能力 |
| **建组后撤销，图层回到原来的位置和层级** | 新能力 |
| **在一个文件夹上撤销"改名字"，名字确实变回去** | 防上面说的"对象身份"坑 |

**最后一条最关键**——它是唯一能抓住"恢复时造了新对象"这个坑的测试。

## 五、问题三：性能如何？嵌套很深会不会慢？

### 直接回答：**嵌套多深都不影响，代价只跟"图层总数"有关，跟"嵌套深度"无关。**

原因：快照存的是**平铺的一整张表**（哪个图层归哪个文件夹管），
不是一棵要递归遍历的树。深度 1 层和深度 50 层，快照大小和恢复时间**完全一样**。

### 具体数字

设图层总数为 N：

| | 现在（记录单行） | 改造后（整份快照） |
| --- | --- | --- |
| 存一次的时间 | 几乎为 0 | 跟 N 成正比，**1000 层约 0.01 毫秒** |
| 存一次的内存 | 几十字节 | **1000 层约 8 KB** |
| 撤销一次的时间 | 几乎为 0 | 跟 N 成正比，**1000 层约 0.01 毫秒** |

撤销栈上限是 **200 步**（`UndoStack.cs:81` 的 `Limit = 200`）。

**最坏情况**：1000 个图层、200 步全是结构性操作 → 约 **1.6 MB**。
作为对比：**一个图层的一幅 4000×3000 像素就是 48 MB。**

### 结论

**性能完全不是问题**，因为省下来的正是"不拷贝像素"这一条。
真正的性能风险不是快照，而是**误把像素也拷进去**——所以我在方案里把
"只存指针"定为硬性约束，并在文档里写明理由。

实际使用中，图层数量是几十到几百这个量级，快照的代价可以完全忽略。

## 六、问题四：能不能分阶段改？

### 能，而且应该。三步，每步都能独立跑绿、独立回滚。

| 步骤 | 做什么 | 风险 | 能否独立验证 |
| --- | --- | --- | --- |
| **第 1 步** | **先补测试**：给现有的新增/删除/复制/排序撤销写测试。让它们在**旧实现**上通过。 | 极低 | ✅ 测试全绿 = 现状被锁住 |
| **第 2 步** | 把「新增 / 复制 / 删除」三种改成像排序那样的整份快照。**同一批测试必须继续全绿。** | 低 | ✅ 测试没改、实现变了、还绿 = 改造正确 |
| **第 3 步** | 引入父子关系后，快照自动就能表达树。补上编组专属测试（删文件夹撤销、建组撤销、改名字撤销）。 | 中 | ✅ 新测试 + 老测试 |

**关键点：第 1 步和第 2 步之间不需要同时存在两套机制。**
新旧两种撤销说明可以共存于同一个撤销栈——每一档自己知道怎么回退自己，互不干扰。
所以**不存在"改到一半不能用"的中间状态**。

第 1、2 步**不依赖编组功能**，现在就能做。第 3 步等编组做完再做。

### 面板缩进阶段用哪套？

**用旧的就行。** 面板缩进只改「显示」，不改「结构」——不新增、不删除、不移动，
所以两套撤销方案都不参与。这也是为什么面板缩进可以紧接着做，不必等这次改造。

### 收益

| | |
| --- | --- |
| 编组/解组/拖拽的撤销**才有可能对** | 不做的话，编组功能做出来撤销就是坏的 |
| **修掉「删文件夹留下悬空子图层」** | 见第二节。**这是我这次模型层改造亲手引进的可达路径**，不是历史遗留——必须由这次改造收尾 |
| 顺带修掉「恢复动作半路静默失败」 | 现在状态对不上会悄悄不做事 |

### 我的建议

**值得做，建议在第 1 步（补测试）之后立刻做第 2 步**，不必等编组功能全部完成。
理由是第 2 步风险低、收益立刻兑现（修掉两个缺陷），
而且**编组功能一旦开始做，撤销就必须已经是新的了**——否则建组做出来的那一刻撤销就是错的。

**一个需要说明的诚实交代**：第二节说的「删文件夹留下悬空子图层」，严格讲不是我这次
模型层改造"发现"的历史遗留问题，而是**我这次改造引入的一条可达路径**——
模型层之前那个 bug 也存在（悬空链接），只是渲染不认父子、所以看不出来。
模型层改造让渲染认了父子，它才变成用户可见的行为。
**这不是"顺便修个老 bug"，这是这次改造欠下的账，应该由这次改造还。**

这不是恢复结构，这是顺手撤销了别的东西。收窄之后语义干净：结构性撤销只恢复结构。

`DeleteLayer` 现在会删掉整棵子树，并在删除前把子节点的 `ParentId` 清掉，
不再留下指向已消失文件夹的悬空链接。**悬空子图层那笔账已还。**

### 改造后实际新增的东西

与下面原方案的差别，以这段为准：

- `LayerStackSnapshot`：存 `List<LayerViewModel>` 顺序 + 每层的
  `ParentId` / `IsGroup` / `BlendMode` / `Mask`。
  **不含 `IsVisible` / `Opacity` / `Name`**（原方案写了，实现时收窄了，理由见上面第 2 步）。
- 恢复时清空并重填 `Layers`，按快照顺序重建文档图层列表，字段写回**同一批** `Layer` 对象。
- `RemoveLayerCore` / `InsertLayerCore` 已删除。

### 为什么恢复时必须保持对象身份

改名字的撤销说明是 `PropertyChange<string>(name, old, new, SetName)`，
它绑定在**某一个具体的 `LayerViewModel`** 上。
如果快照恢复时创建了新的 `LayerViewModel`，那么之后按 Ctrl+Z 去撤销一次改名，
修改的会是那个已经不在文档里的旧对象——**用户看到的是"按了没反应"**。
所以恢复必须复用同一批 ViewModel 实例，只调整它们的顺序和模型字段。

### 顺序恢复的执行方式

按期望顺序从底到顶遍历，把每个图层 `Move` 到它的目标下标。
`Move` 会把目标下标 clamp 到合法范围，并且**跳过"已经在位"的图层**，
所以对已经在正确位置的图层是空操作，整体是 O(N) 次移动。
这条路径已经被 `ApplyPanelOrder` 在生产里用了，不是新代码。

### 快照与像素操作的关系

快照只碰「结构字段」，不碰像素。所以它和现有的像素级撤销
（`PropertyChange<PixelBuffer>`）**完全正交**，不会互相影响。
`LayerViewModel.ReplacePixels` 会重算调整栈，而快照恢复不调用它——
这意味着快照恢复**不会**重算调整，也就不需要担心调整栈的缓存问题。
